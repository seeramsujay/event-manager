# Plan Together: GenAI Event Planning Assistant

[![CI](https://github.com/seeramsujay/event-manager/actions/workflows/ci.yml/badge.svg)](https://github.com/seeramsujay/event-manager/actions/workflows/ci.yml)

An assistant that helps people organize **weddings, birthdays and community events**. You describe your event (date, guests, budget, setting, vibe, priorities and needs) and it builds a plan with:

- **Budget breakdown**: category amounts that add up exactly to your budget and shift toward what you care about most.
- **Timeline**: tasks scheduled backwards from the event date. If you have less time than usual, the schedule is compressed to fit.
- **Vendor checklist**: what to book, how important it is, the date to book it by and a practical tip. You can tick vendors off, and progress is saved in your browser.
- **Context-aware insights**: risks and advice based on your situation, such as a rushed timeline, a tight budget per guest, weather exposure, large crowds, kids, milestone birthdays and accessibility.
- **Personalized ideas**: themes, decor, food, activities and budget tips generated by Claude from your event details. Curated ideas are used when AI is unavailable.

## Chosen vertical

**Event planning assistant.** The persona is a host or organizer: a couple, a parent, a friend or a community volunteer. They are not a professional planner. They need a realistic plan they can act on, and it has to fit their budget and the time they have left.

## Approach and logic

The design is a hybrid: **deterministic rules for decisions, GenAI for creativity.**

Budgets, deadlines and safety-critical tasks such as permits, insurance and weather backups must be reliable and explainable, so a rules engine computes them. The LLM handles the open-ended part, personalized ideas, and it receives the engine's output as grounding context. As a result:

- The plan is always available, fast and free, even with no API key.
- The AI's ideas stay consistent with the computed budget tier and risks.
- Every number and deadline can be traced to a rule and tested.

### Decision logic (`src/planner/`)

| Context signal | Effect on the plan |
|---|---|
| Event type | Selects a profile: default budget split, ideal lead time (wedding 52 weeks, community 16, birthday 8), tasks, vendors and ideas |
| Budget ÷ guests (normalized to USD) | Sets the tier (**lean / moderate / premium**). Lean plans get warnings, DIY nudges on optional vendors and frugal tips |
| Priorities (venue, food, decor, photography, entertainment) | Matching budget categories get ×1.25 weight; matching vendors move up one importance level |
| Outdoor / hybrid setting | Adds a tents & rentals budget line, weather-backup tasks and a rental vendor (essential outdoors); outdoor raises the contingency reserve |
| Lead time shorter than ideal | All deadlines scale proportionally, so order is kept and nothing falls in the past; tasks due within 7 days are flagged; vendors past their usual booking window are marked **Book now**; contingency +2% when under half the ideal time; timeline insight is *critical* below 35% |
| Guest count | Day-of coordinator (weddings ≥150); security and authority coordination (community ≥300); first aid essential (community ≥200) |
| Birthday age | ≤12 is a kids' party (supervision, allergy-safe snacks, no bartender); milestone ages add a tribute task |
| Considerations | Accessibility (interpreter, access plan), low-waste (recycling, local menu), alcohol-free (no bartender, mocktails), kids attending |
| Saturday wedding or birthday | Suggests Friday or Sunday for better rates |
| Food money per guest below a floor | Suggests food trucks, potluck or a dessert format |

Budget amounts are split with the **largest-remainder method**, so they always add up exactly to the total.

### GenAI layer (`src/ai/ideas.js`)

- Calls **Claude (`claude-opus-5-5`)** through the official Anthropic SDK, using **structured outputs** (a JSON schema), so responses are always machine-readable.
- The prompt contains the event context plus the engine's results (tier, top budget categories, key risks). It does not include personal identifiers.
- User free text (vibe, notes) is placed in clearly marked `<vibe>` and `<notes>` sections, and the system prompt treats it as data, not instructions.
- AI output is validated again with Zod: list sizes and string lengths are capped, and empty answers are rejected.
- Server-side refusal fallback (`fallbacks: "default"`) re-runs a declined request on a suitable model.
- Any failure (network, rate limit, refusal, invalid output) falls back to curated ideas with a short notice. The user always gets a plan.
- Identical requests are served from an in-memory LRU cache for one hour to save cost and time.
- Effort is set to `low` because the rules engine has already done the reasoning, which keeps the request responsive.

## How it works

```
Browser (public/)            Node server (src/)
─────────────────            ──────────────────────────────────────────────
form ──POST /api/plan──▶ app.js: rate limit → size/type checks → validation.js (Zod)
                                         │
                                         ▼
                              planner/index.js  buildPlan()  (pure, deterministic)
                               ├─ budget.js     tier + allocation
                               ├─ timeline.js   backward schedule + compression
                               ├─ vendors.js    checklist + priorities
                               └─ insights.js   contextual rules
                                         │
                                         ▼
                              ai/ideas.js  Claude (structured JSON) ─▶ fallback: curated
render ◀────────── JSON plan ────────────┘
```

### Project structure

```
src/
  server.js          entry point: config, Anthropic client, HTTP server
  app.js             request handler: routing, security headers, body limits
  validation.js      Zod request schema + date rules
  planner/           rules engine (catalog data + pure functions)
  ai/ideas.js        Claude integration, prompt, output validation, fallback
  lib/               TTL/LRU cache, rate limiter
public/              accessible static frontend (HTML, CSS, vanilla JS)
test/                node:test suites (unit, HTTP integration, jsdom frontend)
```

## Running it

Requires **Node.js 22.9+**.

```bash
npm install
cp .env.example .env        # optional: add ANTHROPIC_API_KEY for AI ideas
npm start                   # http://127.0.0.1:3000
npm test                    # run the test suite
npm run test:coverage       # with coverage report
```

Without `ANTHROPIC_API_KEY` the app runs in **curated mode**: everything works, and ideas come from a hand-written catalog.

| Variable | Default | Purpose |
|---|---|---|
| `ANTHROPIC_API_KEY` | (none) | Turns on AI-personalized ideas |
| `ANTHROPIC_MODEL` | `claude-opus-5-5` | Model override |
| `PORT` / `HOST` | `3000` / `127.0.0.1` | Listen address |
| `RATE_LIMIT_PER_MINUTE` | `20` | Plan requests per client per minute |

## Quality notes

**Security**
- The API key is used only on the server; the browser talks only to this app.
- Strict request validation: an unknown-field allowlist, typed numbers, enum values, real calendar dates, length limits and stripping of control characters.
- 16 KB body limit, JSON-only content type, per-client rate limiting and a request timeout.
- Strict Content-Security-Policy (`'self'` only, with no inline scripts or styles), `nosniff`, `frame-ancestors 'none'`, `no-referrer` and a Permissions-Policy.
- Static files come from a fixed allowlist preloaded into memory, so path traversal isn't possible.
- The UI renders only through `textContent`, so AI or user text can't inject HTML.
- Error responses never expose stack traces.

**Efficiency**
- Only two runtime dependencies (the Anthropic SDK and Zod); the server uses Node's built-in `http` module.
- The rules engine is pure and runs in about a millisecond. The single LLM call is cached, uses low effort, and is skipped when AI is turned off.
- Static assets are held in memory, and the frontend has no framework or build step.

**Testing**: 49 tests (`node:test`) cover the budget math, timeline compression, conditional tasks and vendors, insights, validation edge cases, the AI path with a mocked client (success, caching, refusals, bad JSON, oversized output), the cache, the rate limiter and the full HTTP stack (headers, error codes, traversal, rate limiting). Frontend tests load the real page in jsdom and check validation messages, focus handling, plan rendering, saved checklist progress, and that AI text containing HTML is shown as plain text. GitHub Actions runs the suite on Node 22 and 24 for every push. Line coverage is about 98%.

**Accessibility**
- Semantic landmarks, a skip link, real `<label>`s, `fieldset`/`legend` groups and a table with headers.
- Field errors are linked with `aria-describedby` and `aria-invalid`, and focus moves to the first error. Status messages use an `aria-live` region, and focus moves to the results heading.
- Fully usable by keyboard, with visible focus rings and colors that meet WCAG AA contrast.
- Dark mode via `prefers-color-scheme` and smooth scrolling only without `prefers-reduced-motion`.
- Responsive layout down to phone width and a print stylesheet for the plan.

## Assumptions

- Budget shares, lead times, tier thresholds and vendor booking windows are typical industry rules of thumb. They are guidance, not quotes.
- Currency conversion uses fixed approximate rates and is used **only** to pick a budget tier. Amounts are shown in the user's currency.
- Dates are calendar days handled in UTC. Plans can be made from today up to 5 years ahead.
- Legal steps (marriage license, permits, insurance) vary by location, so the plan reminds users to check local requirements.
- Vendor checklist progress is stored in the browser's `localStorage` (there are no accounts or server-side storage), so no personal data is kept on the server.
- The rate limiter and cache are in-memory, which suits a single instance. A multi-instance deployment would move them to a shared store such as Redis.
